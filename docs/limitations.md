# Limitations

The honest list, kept in step with the validators that print these caveats - the machine-checked boundary statements below are policed against the code, not maintained by hand. Every entry is a reason not to trust the kit further than it has earned. If a limitation you hit is missing here, that is a documentation bug; file it.

## Boundaries the validators themselves disclose

These three caveats are printed by the enforcement layer at run time; this page represents each one:

- **Covered stacks: JS/TS/JSX-TSX, Python, Go, Rust - no other language family gets the static floors.** A source file outside those families gets a **visible skip** line from the test-honesty gate (its output says `assertion-honesty not evaluated for` that extension) rather than silent acceptance. Disclosed, never silent - but a skip is a skip.
- **The commit-time floors do not evaluate other-stack files at all; Stage V carries the check.** The pre-commit output states this boundary on every commit that stages such files, and the verifier session is where those files get their coverage.
- **The documentation self-check polices specific value classes in a specific doc set** - counted claims, versions, names. It is not a promise that docs can't drift in ways it doesn't model.

## Boundaries of the design itself

- **The ML assurance profile is designed and ratified, but not implemented.** Machine-learning work - training, evaluation, promotion decisions - has a designed part-two profile, ratified and scheduled after this release. Nothing in this version evaluates ML-specific risk.
- **The permission fence is a fence, not a sandbox.** Its deny rules have known bypasses - a subprocess can read what the tool layer would refuse - so keep secrets off disk and use a secret manager plus your operating system's sandbox.
- **The shell write gate is a parser, not a sandbox.** Until the human approves a stage's failing tests, the gate refuses a shell command that writes an implementation file through a recognised write construct (a redirect, `tee`, `sed -i`, `cp`, `mv`, `truncate`, `node -e` or `node -p`, a PowerShell `Set-Content` or `Clear-Content`, and the others the hook lists), and one whose target it cannot read; in every state it refuses one that deletes, moves or writes one of its own control files, `git clean -x` and `git stash -a` among them. It reads a construct at any nesting it can parse, up to eight levels deep: inside `$(...)`, backticks and process substitutions, inside an unquoted heredoc body, an arithmetic expansion and a parameter expansion, after keywords such as `then` and `do`, inside PowerShell script blocks, and inside `bash -c`, `sh -c`, `zsh -c`, `eval`, `pwsh -c` and `powershell -Command` when their text is literal. A body nested deeper or never closed, a wrapper whose text is not literal, and a deletion whose target it cannot read (one that arrives on a PowerShell pipeline or through `xargs` among them) are refused while a stage is engaged (open, its failing tests not yet approved). It judges nothing else: a script or program that writes a file itself, an alias, an interpreter without a literal path in the command, `cmd /c`, `Invoke-Expression`, `env -S`, `find -exec`, `find -delete`, `ln` and `dd` are not judged, and a shell working folder carried over from an earlier command is not seen.
- **The gate's own scripts are held by their form and by the recorded prompt, not by who runs them.** The hook lets `approve-red.cjs` and `stage-active.cjs` run only in their bare forms, which the fence always asks about under the Bash tool, and from a Claude Code session the release, the void and the clear refuse unless the prompt the command asked is on record in the session's receipts (deterministic enforcement). The kit sets no ask rule for Claude Code's PowerShell tool, which is on automatically on Windows without Git Bash, opt-in elsewhere with `CLAUDE_CODE_USE_POWERSHELL_TOOL=1`, and off on Windows with Git Bash while the kit's Bash deny rules stand, unless that variable is set; under it the hook refuses any command that names either script or one of the gate's control files unless it is a bare form, and the recorded prompt still holds (deterministic enforcement). From your own shell, outside the Claude Code session, both scripts run with no session id and need no recorded prompt (human authorization), and a wrapper that clears the session id before running either one reaches that same path, as the hook does not judge a script that names either one inside a file, nor a command's own inline program that builds the name from pieces (for example a `node -e` program that joins two strings); from a session, the release, the void and the clear reached that way still refuse without a recorded prompt, and the open takes no click, since opening engages the gate (deterministic enforcement). Any permission prompt from the last two minutes also counts, not only the one for that command, parallel tool calls can make another call's prompt the newest, and the receipts ledger is a file the session's own tools can write, so the record shows that a prompt was recorded, not who answered it (observed evidence, never authorization).
- **The hook's reading of PowerShell is its own.** Under the PowerShell tool the hook reads a command with its own lexer, which follows PowerShell's written quoting, comment, white-space and grouping rules, and real PowerShell checks that reading on a corpus of forms wherever `pwsh` is installed (deterministic enforcement, checked against observed evidence); a form outside the corpus where the two readings differ can still hide a write to an ordinary file, which is why under that tool the gate's own names are judged by name and never by the reading. One such form is known: PowerShell reads a typographic dash (an en dash, an em dash or a horizontal bar) before a parameter name as `-` and the hook does not, so a cmdlet's file operand can bind where the hook does not look (observed evidence, run on pwsh 7.6.9); the fix, judging such a command with PowerShell's own parser, is planned for a later release. The stop-parsing token `--%` is read as PowerShell reads it: the rest of its line is literal text, judged as a command list, and no quote in it reaches the next line (deterministic enforcement).
- **The evidence records are checked against each other and the commit, never against their author.** A stage's RED and GREEN records, the gate's judgments and the lane's result are bound to the tested files and checked by `node scripts/evidence.cjs --stage <id> --verify` (deterministic enforcement over observed evidence), but anyone who can write the repository can rewrite a record together with its manifest and the check still passes: a fabricated record is outside the local trust boundary the evidence path claims. The first evidence path supports one host (Claude Code at 2.1.295 or later), one test runner reading (`node --test`) and one transport; anything else is unsupported on this path.
- **The calibration seal is a check after the fact, not a file block.** The verifier's exam is void when the session's read record shows a read of a sealed answer file (deterministic enforcement over the recorded reads), but nothing stops the read, a glob, a directory search or another program is outside the record, and a file outside the answer folder that carries the answers (an earlier exam's findings, for example) is not refused. The exam is only as blind as the verifier's reads (agent judgment).
- **The human stamp is load-bearing.** You do not need to read the code - but the gates assume the human who stamps each stage has read the agent's review and the orchestrator's comments and run any live testing. Rubber-stamp them and every control in the kit degrades to ceremony. The framework's own data says the human review is the one control that cannot be automated away.
- **Token cost is higher than a plain instruction file.** A session starts on a short stamp and reads each entry on its reading list at the moment it needs it, with every read recorded, which bounds the cost - but a framework of this size still costs more to run than a bare `CLAUDE.md`.
- **No controlled study shows this approach beats a concise instruction file plus tests plus code review.** The design is a reasoned bet on the published evidence, not a demonstrated win.
- **The cost against a lighter loop is not measured on this release.** The trial that measured it ran on an earlier release, before the weight was cut; that result no longer describes the kit, and it is being re-run. The result will be published here.

## Boundaries of this release

- **Verified on Windows and Linux; macOS is field use only.** Linux CI (`ubuntu-latest`, Node 24) is the authoritative verification environment and Windows (Node 22+, Git, PowerShell or Git Bash) the development floor; there is no platform matrix. Outside users have run builds on macOS, but no macOS verification run exists.
- **Pin a tag; do not track the default branch.** Releases are snapshots of a privately developed kit. Interfaces may still change between releases; pin the tag you verified.
- **No worked example ships.** The build receipt included as evidence is real, but it is not a guided walkthrough.
- **No human security audit has been performed.** None is claimed. See [SECURITY.md](../SECURITY.md).
- **Pull requests are not accepted.** Development is private and this is a published snapshot; issues are read, and no response time is promised.

The full context for each release-scoped item is in [RELEASE-NOTES.md](../RELEASE-NOTES.md); the when-not-to-use-this cases are in [WHY-THIS-KIT.md](../WHY-THIS-KIT.md).
