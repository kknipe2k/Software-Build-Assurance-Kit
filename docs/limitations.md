# Limitations

The honest list, kept in step with the validators that print these caveats - the machine-checked boundary statements below are policed against the code, not maintained by hand. Every entry is a reason not to trust the kit further than it has earned. If a limitation you hit is missing here, that is a documentation bug; file it.

## Boundaries the validators themselves disclose

These three caveats are printed by the enforcement layer at run time; this page represents each one:

- **Covered stacks: JS/TS/JSX-TSX, Python, Go, Rust - no other language family gets the static floors.** The test-honesty gate prints a **visible skip** line for a test file of another family that it recognises (its output says `assertion-honesty not evaluated for` that extension) and a named skip line for a recognised JS/TS test file in which it finds no test; a recognised Python, Go or Rust test file in which it finds no test, and a test file it does not recognise, get no line at all (the test-honesty entry below names which). A skip is a skip.
- **The commit-time floors do not evaluate other-stack files at all; Stage V carries the check.** The pre-commit output states this boundary on every commit that stages such files, and the verifier session is where those files get their coverage.
- **The documentation self-check polices specific value classes in a specific doc set** - counted claims, versions, names. It is not a promise that docs can't drift in ways it doesn't model.

## Boundaries of the design itself

- **The test-honesty gate checks the bytes that commit, for presence, not effectiveness.** It judges the staged copy of each test file it recognises, the copy that commits, renames included, and sees the JS/TS forms `test.each`, `it.only`, `.skip` and `.concurrent` (deterministic enforcement). It checks that a test has an assertion, not that the assertion is effective: Stage V's plan-challenge judges that (agent judgment). Today only a Ruby test file gets the visible skip line; a Rust unit test inside `src/` and the test files of other families (Dart, Java) get no line at all, and an assertion written inside a string or a docstring satisfies the check; both gaps are known and planned for a later release. Its severity is the `test_honesty` row of `project-config.md`, read as written: the kit does not check who set it, so an agent session can stage `warn` and the next commit passes with a NOTE; `kit-update --ready` names a value changed since the bootstrap commit (observed evidence).

- **The spec chain proves where the live spec came from, not that a change was wise.** From the bootstrap commit on, the commit floor refuses a staged change to the original spec (`spec/project-spec.md`) and a live spec (`spec/live-spec.md`) its hash chain does not reach (deterministic enforcement); a warn severity in `project-config.md` does not loosen it, and neither does its Tier line: once the chain is committed the floor checks every spec commit whatever that line reads, and the file check and `--closeout` walk any chain on disk (deterministic enforcement). That holds in a project that carries the spec-chain validator (`validators/validate-spec-chain.cjs`), and the kit starts a chain only there: the freeze and the change record are the validator's own, and `kit-update --migrate` splits a spec only in a project that carries it, leaving the spec of one that does not as it is and saying so on its spec line (deterministic enforcement). A chain written by hand in a project that does not carry the validator is not checked: each commit there that stages a `spec/` path prints the gate-not-rendered note and goes through (deterministic enforcement). It does not judge whether a recorded change was a good one, and `git commit --no-verify` skips it, as it skips every commit-floor check. A project whose spec was committed before the live spec existed has no chain, so its spec edits are not checked until `kit-update --migrate` splits it; one n/a line says so on each such commit in a project that carries the validator. A project that already holds a `spec/live-spec.md` with no chain is never split (the migration leaves it as it is), so its spec edits stay unchecked (deterministic enforcement).
- **A requirement change's approval line is the person's typed word, recorded as text.** The commit floor refuses a live-spec edit with no change file in the same commit and a change whose sha256 before and after do not chain (deterministic enforcement). The approval line is checked for being filled, not for who wrote it, and a change file's Milestone line is written by the person or the agent (agent judgment): a change filed under the wrong milestone is listed by that milestone's closeout, while every closeout states how many of the chain's changes it lists. A change must name requirement ids the live spec defines: `--change` refuses an id the live spec defines neither before nor after the change (the previous link's bytes, from git or the original; where neither holds them, the commit's start) and the commit floor one it defines neither before nor after the commit that carries the change, naming the id (deterministic enforcement); whether those are the ids its edit changed, its contract text and its named tests are the change file's words, not compared with the live spec, so a closeout lists the ids a change names (agent judgment).
- **Requirement to assertion is a first step only.** A change file names the tests for the requirements it touches, and the stage that implements the change carries them in its RED; whether those tests assert the right result is not checked by the kit (the reviewer's judgment, agent judgment). The verifier's and the refactor's reading lists name the original spec, which exists at every tier; their read of the live spec beside it is asked by the list's description, not by an entry the read-first check enforces (agent judgment).
- **The spec challenge is a second look, not a proof.** At Full the freeze and the bootstrap commit refuse a spec with no challenge record (`spec/spec-challenge.md`), a read set beyond the draft spec and the discovery notes, a run with no findings row and a missing sign-off line (deterministic enforcement). The record is text: the kit does not check that the challenge ran in a fresh session (a subagent or a new session), what it read, whether its findings were folded honestly, or who signed (agent judgment and human authorization). The record and the discovery notes are not hashed into the spec chain, so an edit of them after the freeze is not refused. A requirement the challenge did not find stays missed until a change file adds it, and a project frozen before this check, or split by kit-update --migrate, carries no challenge record.
- **The forecast label is checked by keyword, in the kit's own documents.** The doc check refuses a sentence in the kit's documents it scans that labels a performance, scale or future-behaviour claim observed evidence with no record named beside it, and a forecast label that names no assumption (deterministic enforcement). It does not run in a project: a project's sentences, and a claim worded outside its keyword list, are the reviewer's to read (agent judgment). Within the kit's documents it checks that a record is named beside such a claim, not that the record exists, and it reads one line at a time, so a label wrapped onto the next line is not seen (deterministic enforcement); those, and a claim that carries no label at all, are the reviewer's to catch (agent judgment).
- **The ML assurance profile is designed and ratified, but not implemented.** Machine-learning work - training, evaluation, promotion decisions - has a designed part-two profile, ratified and scheduled after this release. Nothing in this version evaluates ML-specific risk.
- **The permission fence is a fence, not a sandbox.** Its deny rules have known bypasses - a subprocess can read what the tool layer would refuse - so keep secrets off disk and use a secret manager plus your operating system's sandbox.
- **The shell write gate is a parser, not a sandbox.** Until the human approves a stage's failing tests, the gate refuses a shell command that writes an implementation file through a recognised write construct (a redirect, `tee`, `sed -i`, `cp`, `mv`, `truncate`, `node -e` or `node -p`, a PowerShell `Set-Content` or `Clear-Content`, and the others the hook lists), and one whose target it cannot read; in every state it refuses one that deletes, moves or writes one of its own control files, `git clean -x` and `git stash -a` among them. It reads a construct at any nesting it can parse, up to eight levels deep: inside `$(...)`, backticks and process substitutions, inside an unquoted heredoc body, an arithmetic expansion and a parameter expansion, after keywords such as `then` and `do`, inside PowerShell script blocks, and inside `bash -c`, `sh -c`, `zsh -c`, `eval`, `pwsh -c` and `powershell -Command` when their text is literal. A body nested deeper or never closed, a wrapper whose text is not literal, and a deletion whose target it cannot read (one that arrives on a PowerShell pipeline or through `xargs` among them) are refused while a stage is engaged (open, its failing tests not yet approved). It judges nothing else: a script or program that writes a file itself, an alias, an interpreter without a literal path in the command, `cmd /c`, `Invoke-Expression`, `env -S`, `find -exec`, `find -delete`, `ln` and `dd` are not judged, and a shell working folder carried over from an earlier command is not seen.
- **The gate's own scripts are held by their form and by the recorded prompt, not by who runs them.** The hook lets `approve-red.cjs` and `stage-active.cjs` run only in their bare forms, which the fence always asks about under the Bash tool, and from a Claude Code session the release, the void and the clear refuse unless the prompt the command asked is on record in the session's receipts (deterministic enforcement). The kit sets no ask rule for Claude Code's PowerShell tool, which is on automatically on Windows without Git Bash, opt-in elsewhere with `CLAUDE_CODE_USE_POWERSHELL_TOOL=1`, and off on Windows with Git Bash while the kit's Bash deny rules stand, unless that variable is set; under it the hook refuses any command that names either script or one of the gate's control files unless it is a bare form, and the recorded prompt still holds (deterministic enforcement). From your own terminal, outside the Claude Code session, both scripts run with no recorded prompt (human authorization), except under a test runner or a package script, or where the process tree cannot be read; a wrapper that only clears the session id no longer reaches that path, because the process tree decides (deterministic enforcement), but a process that leaves the session's tree does (a script on the same account), as the hook does not judge a script that names either one inside a file, nor a command's own inline program that builds the name from pieces (for example a `node -e` program that joins two strings); from a session, the release, the void and the clear reached that way still refuse without a recorded prompt, and the open takes no click, since opening engages the gate (deterministic enforcement). Any permission prompt from the last two minutes also counts, not only the one for that command, parallel tool calls can make another call's prompt the newest, and the receipts ledger is a file the session's own tools can write, so the record shows that a prompt was recorded, not who answered it (observed evidence, never authorization).
- **The hook's reading of PowerShell is its own.** Under the PowerShell tool the hook reads a command with its own lexer, which follows PowerShell's written quoting, comment, white-space and grouping rules, and real PowerShell checks that reading on a corpus of forms wherever `pwsh` is installed (deterministic enforcement, checked against observed evidence); a form outside the corpus where the two readings differ can still hide a write to an ordinary file, which is why under that tool the gate's own names are judged by name and never by the reading. One such form is known: PowerShell reads a typographic dash (an en dash, an em dash or a horizontal bar) before a parameter name as `-` and the hook does not, so a cmdlet's file operand can bind where the hook does not look (observed evidence, run on pwsh 7.6.9); the fix, judging such a command with PowerShell's own parser, is planned for a later release. The stop-parsing token `--%` is read as PowerShell reads it: the rest of its line is literal text, judged as a command list, and no quote in it reaches the next line (deterministic enforcement).
- **The evidence records are checked against each other and the commit, never against their author.** A stage's RED and GREEN records, the gate's judgments and the lane's result are bound to the tested files and checked by `node scripts/evidence.cjs --stage <id> --verify` (deterministic enforcement over observed evidence), but anyone who can write the repository can rewrite a record together with its manifest and the check still passes: a fabricated record is outside the local trust boundary the evidence path claims. The first evidence path supports one host (Claude Code at 2.1.295 or later), one test runner reading (`node --test`) and one transport; anything else is unsupported on this path.
- **The calibration seal is a check after the fact, not a file block.** The verifier's exam is void when the scorer, run with the verifier's `--session`, or `--check verify` finds a read of a sealed answer file in the session's read record (deterministic enforcement over the recorded reads); a score made without `--session` says `labels-unread: not checked`, and running it with `--session` is the orchestrator's step (agent judgment). Nothing stops the read, a glob, a directory search or another program is outside the record, and a file outside the two answer folders (`prompts/calibration/labels/` and `sbak/prompts/calibration/labels/`) that carries the answers (an earlier exam's findings, for example) is not refused. The exam is only as blind as the verifier's reads (agent judgment).
- **The human stamp is load-bearing.** You do not need to read the code - but the gates assume the human who stamps each stage has read the agent's review and the orchestrator's comments and run any live testing. Rubber-stamp them and every control in the kit degrades to ceremony. The framework's own data says the human review is the one control that cannot be automated away.
- **The stamp's record shows the prompt your session received, not who held the device.** The orchestrator session's UserPromptSubmit hook records each prompt's sha256 and turn, typed or delivered from another session, and accept takes a stamp only when a prompt typed in that session after the stage-end packet carries its text, surrounding white space aside (deterministic enforcement over your typed word, human authorization); a prompt you type from your phone through Remote Control reads the same (it reaches the hook, observed in the kit's own testing; its payload was not captured). What the record cannot tell: a scheduled prompt, an accepted prompt suggestion, a prompt a program sends through the CLI and your word typed into the wrong session all read as typed, the receipts ledger is writable by the session's own file tools and by any program on your account, and a short prompt's sha256 can be matched by guessing it (observed evidence). With no orchestrator worktree, where no accept runs, a stage commit carries no accept: the pre-commit checks the bundle's content (deterministic enforcement) and the commit's own permission prompt is your word (human authorization). `node scripts/set-mode.cjs`, run in the orchestrator's tree, is not judged by the red gate: a flip to work there makes the pre-commit read one tree (the bundle's content only), while the commit still asks you.
- **A direct push is checked by the pre-push hook only, and an exception line is not checked for its author.** The append-only workflow runs on pull requests; a push straight to a branch the kit does not protect is checked by the pre-push hook alone (deterministic enforcement on the pushing machine), `git push --no-verify` skips it, and the kit sets no branch protection, so that is the repository owner's choice (human authorization). A line in `docs/append-only-exceptions.txt` records an approval; the checker reads its shape (a 7 to 40 hex sha, a path, a reason) and applies it only at a walked commit whose sha starts with that prefix, for the path it names, and every run prints the lines it honors (deterministic enforcement), but it does not check who wrote the line (an agent session can write that file), nor that the commit exists. A new branch is walked from its merge-base with this clone's copy of the remote's default branch, and a remote sha this clone lacks is refused (fetch, then push).
- **The kit chains your own git hooks as they were at the install; it cannot judge them.** The installer and adopt read the hooks your repository already runs before they write anything and change them only on your word (human authorization): on `chain` the kit's pre-commit and pre-push run yours first, with git's arguments and input, and a refusal from either refuses the commit or the push (deterministic enforcement); on `replace` yours stop running and the previous setting is recorded in git config (`sbak.hooksReplaced`) and, by the installer, in `sbak/INSTALL.log` and `sbak/INSTALLED.json` (observed evidence). The chain cannot tell a hook of yours that checks nothing from one that checks something. The chain is declared in this clone's git config (`sbak.hooksChain`): another clone runs none of the kit's checks until its hooks path is set, and after `node scripts/install-hooks.cjs` it runs them with no chain until adopt runs there and asks (deterministic enforcement); a hook of another name added to your folder later runs only after the next adopt. On a branch or checkout that does not carry the kit's `.githooks/` folder, git runs no hook at all, yours included. A tool that sets `core.hooksPath` again turns the kit's checks off until adopt runs again: husky 9 does this on every `npm install` (its `prepare` script). The installer asks and adopt stops to name the two words; `node scripts/install-hooks.cjs`, the step after cloning a project that already uses the kit, still sets the hooks path without asking. An install of v1.0.10 or older that replaced your hooks recorded nothing, and the upgrade, which sees the kit's hooks path in effect, asks nothing: that loss cannot be recovered from the kit's side.
- **An installer already published keeps its behaviour.** The installer's refusals of a downgrade, of a link and of a repository inside another are in the installer from this release on (deterministic enforcement); an installer of v1.0.10 or older run over a newer install still offers it as an upgrade, so run the installer of the release you want, from the releases page (human authorization).
- **The Copilot path keeps your files only when you run its lines as printed.** Its extract (`unzip -n`; on Windows `tar -xkf`) never replaces a file you already have, and the kit's instructions reach `.github/copilot-instructions.md` from the ZIP only where you have none (deterministic enforcement, run as printed). An extract run the older way (a plain `unzip`, or `tar -xf`, which on Windows replaces a `CLAUDE.md` of yours silently, an uncommitted one beyond recovery) still replaces it (observed evidence); and where your repository already has a `copilot-instructions.md`, the kit's rules reach Copilot only once you add them to it yourself (human authorization).
- **Three settings outside the project switch its hooks off, and the project cannot see them.** A session started with `disableAllHooks` set to true in your user settings or passed with `--settings`, with `--setting-sources` leaving out `project`, or with `--bare` runs with none of the project's hooks: no red gate, no read-first stamp, no receipts (Claude Code's documentation for `disableAllHooks` and `--bare`, which also skips `CLAUDE.md`; observed for `--setting-sources user` on Claude Code 2.1.322, which also left out the project's deny rules and `CLAUDE.md`). `kit-update --ready` reads only the project's own settings files, so it reads READY in such a session (observed evidence), and nothing in the project can stop a setting you pass (human authorization). Where the kit's prompt hook does run, a session with no stamp is stopped at its first prompt (deterministic enforcement).
- **Who is at the keyboard is bar-raised, not proven.** No local binding tells you from a script running on your account: a process that leaves the session's process tree reads as your own terminal, since the check reads the tree, not the person (deterministic enforcement over the tree). A platform-authenticator signature (Face ID, fingerprint, Windows Hello) is the planned opt-in for business users in corporate environments, on request and never the default; it is not in this release. A push run from inside an allow-listed command has no click check, and an allow-listed program that runs code the agent wrote (the test command running a test the agent wrote, for example) is outside every ask rule and hook. The red gate and the ask rules are a bar-raise, not a wall.
- **The git fence reads the forms it names.** It asks for `git commit` and `git push` by git's own grammar, aliases resolved (deterministic enforcement), but not inside a script file, through `xargs`, `find -exec`, `iex` or `Start-Process`, or from a variable command word; not an external `git-<name>`, a verb git adds after 2.43.0, or another commit-making command (`commit-tree` with `update-ref`, `send-pack`). Where Windows PowerShell 5.1 cannot run (a policy block), the gate scripts refuse on that machine until it can; under a Flatpak terminal (bwrap tops it too) a release with an empty session id is refused: run it from a terminal outside the sandbox, or in the session.
- **Removing the kit is a manual list in this release.** This release ships no removal command; one comes with the install route table in a later release. To remove the kit, undo what the install, adopt and the bootstrap wrote, in this order (human authorization; nothing checks the result):
  - git's hooks path first: `sbak/INSTALL.log`'s `hooks restore:` line lists the commands in order (the previous `core.hooksPath` set or unset, each hook of yours the install moved renamed back, each forwarder it wrote removed); then `git config --unset sbak.hooksChain` or `git config --unset sbak.hooksReplaced`, whichever is set. Adopt run by hand records in git config only; with no record at all, `git config --unset core.hooksPath`.
  - `.claude/`: its `settings.json` merged yours, so restore the oldest `.claude/settings.archive/<time>.settings.json` (your file before the first merge) to `.claude/settings.json`, then delete what the kit wrote there (its hooks, commands, skills, read-first lists, `red-gate-allow.txt` and its markers); `.claude/evidence/`, `.claude/receipts/` and `.claude/channel/` hold your project's records: keep them or delete them.
  - delete `sbak/`, the installer's download folder where it was left, `.githooks/`, the kit's files under `scripts/` (`sbak/release-manifest.json` names them) and the bootstrap's `validators/`, `prompts/` and root `ORCHESTRATOR.md`, and the workflows it generated under `.github/workflows/` (`pr-smoke.yml`, `release.yml`, and `append-only-ledger.yml` where a risk trigger was declared).
  - the root `.gitattributes`, where the install wrote it (its report and `sbak/INSTALL.log` name it).
  - `CLAUDE.md`: remove the `@sbak/CLAUDE.md` import line from yours; where the bootstrap placed `CLAUDE.sbak.md`, delete it and its import line; where the bootstrap replaced the kit's `CLAUDE.md` with your project's, that file is your project's.
  - kept: your documents (`docs/`, `spec/`, `project-config.md`, `README.md`, `CHANGELOG.md`, `LICENSE`, `.gitignore`), your retrospectives (`retrospectives/`) and ledgers, and a repository the install created.
- **The kit's line-ending rule rewrites your batch files on Windows.** Under Git for Windows' default `core.autocrlf=true`, the root `.gitattributes` the install writes (`* text=auto eol=lf`) lands your `.bat` and `.cmd` files with LF endings on their next checkout, a clone or a branch switch (observed evidence). cmd runs most LF batch files, but a label or a `goto` can misread: give them `*.bat text eol=crlf` and `*.cmd text eol=crlf` lines in `.gitattributes` (your choice; the kit does not write them).
- **Token cost is higher than a plain instruction file.** A session starts on a short stamp and reads each entry on its reading list at the moment it needs it, with every read recorded, which bounds the cost - but a framework of this size still costs more to run than a bare `CLAUDE.md`.
- **No controlled study shows this approach beats a concise instruction file plus tests plus code review.** The design is a reasoned bet on the published evidence, not a demonstrated win.
- **The cost against a lighter loop is not measured on this release.** The trial that measured it ran on an earlier release, before the weight was cut; that result no longer describes the kit, and it is being re-run. The result will be published here.

## Boundaries of this release

- **Verified on Windows and Linux; macOS is field use only.** Linux CI (`ubuntu-latest`, Node 24) is the authoritative verification environment and Windows (Node 22+, Git, PowerShell or Git Bash) the development floor; there is no platform matrix. Outside users have run builds on macOS, but no macOS verification run exists.
- **Pin a tag; do not track the default branch.** Releases are snapshots of a privately developed kit. Interfaces may still change between releases; pin the tag you verified.
- **No worked example ships.** The build receipt included as evidence is real, but it is not a guided walkthrough.
- **The build receipt renders a structured field as written.** The collectors take a verdict, a RED-first control or a fix only from a structured line holding a word from a closed list or a named commit (deterministic enforcement), and they check its shape, not its truth: a `red-first:` line is not proof that the test failed, a `fix:` line is not proof that the commit fixed it, and the receipt does not show who wrote the line (agent judgment, recorded as written).
- **No human security audit has been performed.** None is claimed. See [SECURITY.md](../SECURITY.md).
- **Pull requests are not accepted.** Development is private and this is a published snapshot; issues are read, and no response time is promised.

The full context for each release-scoped item is in [RELEASE-NOTES.md](../RELEASE-NOTES.md); the when-not-to-use-this cases are in [WHY-THIS-KIT.md](../WHY-THIS-KIT.md).
