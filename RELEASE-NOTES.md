# Release notes - v1.0.11

**This is the current GA release of the Software Build Assurance Kit: the live spec, and the feature walk's fixes.** The 1.0 bar is an integrity bar, not a feature bar: five decision-record properties, each demonstrated absent-of-defect **by execution** on verifier-built fixtures, in the authoritative CI environment. The evidence trail for every claim below is public in this repository's checks and in `example-receipt.html`.

Read this page before you adopt the kit for anything you care about. It says what works, what does not, and what evidence backs each claim. The release history in the same shape is in [CHANGELOG.md](CHANGELOG.md).

## What v1.0.11 changes

Two things. A project's spec becomes two files, so what was first agreed and what is true now can no longer be confused, and a requirement change leaves one approved record the commit floor can follow. And the previous release was walked feature by feature as a person meets it: 22 defects were found and every one is closed here. The build loop does not change, and the Claude Code floor stays at 2.1.295.

### The live spec

- **The original spec is frozen and a live spec carries the changes.** At the bootstrap commit `node validators/validate-spec-chain.cjs --freeze` writes `spec/live-spec.md` as a byte copy of `spec/project-spec.md` and `spec/spec-chain.json` with both hashes. From then on the commit floor refuses an edit of the original and a live spec its hash chain does not reach (deterministic enforcement). Requirements carry `REQ-` ids and the spec an Assumptions section, each assumption with what would show it false.
- **One change file per requirement change.** A change is one file under `spec/changes/`, written from `prompts/SPEC-CHANGE-TEMPLATE.md` (five fields and your approval line), recorded with `--change` and committed in the same commit as the live-spec edit, or the commit is refused (deterministic enforcement). A change must name requirement ids the live spec defines before or after the commit that carries it. The milestone closeout prints what changed, or the one line "no requirement changed".
- **Two looks before the freeze.** Before the original is frozen a fresh-context session challenges the draft spec against your discovery answers, reading only the draft and `spec/discovery-notes.md`; its findings and your sign-off are recorded in `spec/spec-challenge.md`, with a second person's sign-off where you have one or the words "no second person". The freeze refuses a spec without that record (deterministic enforcement). The kit records the text; it does not check that the session was fresh or who signed.
- **A fifth label, forecast.** A claim about conditions not exercised (a performance, a scale, a behaviour in the future) is labelled forecast with its assumptions named, and is never written as observed evidence.
- **The floor follows the chain, not the tier line.** A project that carries a spec chain is checked whatever its `Tier` line reads (deterministic enforcement).

### What the feature walk fixed

- **The kit's own controls are out of the agent's reach.** The commit floor's files and the channel's files are in the control set and the deny floor, the pre-commit checks itself and its validators against the release manifest, and the secret files' family is denied whole, `.env.example` included.
- **The person's acts need the person.** The gate scripts decide whether a person is at the terminal from the process tree and refuse under a test runner; the release keystroke is bound to its session, its turn and a pending release; the stamp is recorded from the typed prompt and the acceptance checked against it (deterministic enforcement over the typed word, human authorization).
- **Your existing git hooks are found before anything is written.** The installer and adopt report them and chain or replace them only on your word, recording the previous value.
- **Readiness and adopt are judged by content.** The git hooks, the managed files and the Done line are read by what they contain, and readiness runs a small smoke with a pre-commit fixture, so a hook that is present and does nothing no longer reads ready. An edited kit file that a migration kept reads NOT READY until you declare it an INTENTIONAL DIVERGENCE.
- **The installer writes only where it says.** Never through a symlink, never into a nested repository, every root write reported, a downgrade named, and the manual path keeps your `CLAUDE.md`.
- **A resolved migration conflict stays resolved.** The re-run raises the pin, and a token-bearing hunk merges on its own line.
- **Scope and append-only checks read the right bytes.** The scope record is compared at the index as well as HEAD; the append-only check reads the ledger list at the base too, and the push check walks the refs being pushed.
- **The receipt and the mutation line read committed, structured records.** The receipt takes a claim only from a structured field and prints UNKNOWN where nothing ran; on the Full path a new work-stage retrospective needs its handoff note with a named mutation, or `n/a - <reason>`.
- **The shipped text was swept.** The config toggle that claimed to switch hook enforcement is retired (the hooks never read it), the Copilot extract keeps your files, the cmd launch line uses the quoted `set` form, and the routes that switch the project layer off are named.

### Upgrading a v1.0.10 project

Run the same command as the install: download this release's `sbak-install.cjs` into the project folder, start `claude` there, type `sbak-install`, and answer `upgrade`. Commit the upgrade, then run `node scripts/kit-update.cjs --migrate`: the table first, then `--apply-all` to write; it refuses an uncommitted tree (deterministic enforcement).

- **Your spec is split.** In a project that carries the spec-chain validator the migration freezes `spec/project-spec.md` as it is, writes `spec/live-spec.md` as its copy and starts the chain; its `spec:` line says so before anything is written. The first change to the live spec adds the `REQ-` ids it names and the Assumptions section. In a project that does not carry the validator the migration leaves the spec as it is and says so on the same line.
- **A conflict you resolved by taking the release side** in an earlier migration may have left an unfilled `{{TOKEN}}`; `.claude/kit-migrate.json` names the files.
- **The example receipt** is regenerated at each release, and the release build refuses a stale one.

### Carried from the previous release, unchanged

The previous release's work, the gate attests itself:

- **Each stage's evidence is a record.** The RED and GREEN runs are written under `.claude/evidence/<stage>/`, bound to a fingerprint of the files they tested, and the stage end, the pre-commit check and the push check read the records against the tree.
- **The verifier's exam is scored by someone else.** The verifier judges the seeded-defect set blind and writes verdicts only; the orchestrator scores them against the sealed answers with `node scripts/calibration-score.cjs`. A recorded read of an answer file, in either copy of the answers a project holds (`prompts/calibration/labels/` or `sbak/prompts/calibration/labels/`, before and after an upgrade), voids the exam when the check runs: the scorer refuses with the verifier's `--session`, and `--check verify` refuses in the verifier's session (deterministic enforcement over the recorded reads); running the scorer with `--session` is the orchestrator's step (agent judgment). That check runs on the session's read record after the fact; it is not a file-access block (see Limitations).
- **The gate's own scripts run only as asked.** `approve-red.cjs` and `stage-active.cjs` run only in their bare forms, and the release, the void and the clear refuse unless the prompt the command raised is on record.
- **The PowerShell tool is read as PowerShell reads it,** and the hook refuses a command naming a gate script or a control file unless it is a bare form.
- **What used to be remembered, a program now does:** the orchestrator's ordinary messages leave on its own authority, a stage opens only while the orchestrator listens, `kit-update --ready` prints the leaving-bootstrap block, and the installer says before the download whether `gh` can check the attestation.
- **The gate fails closed on its own faults,** the shell write gate refuses what it cannot read (it is a parser, not a sandbox), an approval that stops standing is void, a rejected attestation installs nothing, and the settings file has one door (`node scripts/kit-update.cjs --place-settings <filled-file>`).
- **One readiness result.** `kit-update --ready` prints one line per check and one next command, reads the three markers the way the hook's probe does (a one-line approval marker beside a v2 approval record, which the hook reads as unknown, is not among them), and an upgrade ends on the same block.

## What GA means here

The GA decision record required, and independent verification confirmed by execution:

1. **Adoption never mutates outside the project root** - symlink escapes (external, internal, dangling) are refused at every install site, targets byte-untouched, loudly and non-zero.
2. **Adoption never reports success with controls dormant** - hook wiredness is parsed, not pattern-matched; where the kit's prompt hook runs, a session whose read-first stamp is missing is stopped at its first prompt, naming the missing stamp (deterministic enforcement), and where a session's hooks are off (`disableAllHooks`, `--setting-sources` without `project`, `--bare`) nothing fires.
3. **The release verification lane has no silent or required skip** - every task appears in the run's own machine-readable summary with a verdict; a required skip is a failure, never a pass.
4. **POSIX hook liveness is proven, not assumed** - rendered hooks execute on Linux CI with the executable bit asserted; a Windows-local green is disclosed as non-authoritative at the point of use.
5. **A failed settings merge cannot destroy user settings** - byte-exact archive, atomic replace, auto-restore proven on a planted mid-write failure; unparseable settings are never replaced.

Each was verified twice: by the framework's own gates, and by an independent fresh-context verifier session that built its own fixtures and reproduced the release lane in a pristine clone.

## Capabilities

- **A bootstrap that asks what you are building and derives the rest.** It infers the operating mode from your description, derives the risk posture from the spec, and shows the calibration as one acceptance line. Everything else is derived by a script from a single authority file and surfaced with its one-line why.
- **One-file install and upgrade.** `sbak-install.cjs`, attested beside the ZIP, drives the whole install from inside `claude` - checksum and attestation verified, blast radius disclosed, its questions one step at a time, nothing written before your word - and upgrades an installed kit the same way, keeping what you modified and naming the bootstrap-filled files it leaves at the installed version.
- **A channel between the two terminals.** Stage packets and verdicts travel between the orchestrator and the builder over an append-only log with automatic pickup - `/listen` puts a session on watch, and the orchestrator's messages leave on its own authority - and the verifier and refactorer sessions use it too; the release remains the human's click on its prompt in the build window (human authorization), and `/send --approval` carries the orchestrator's verdict to it. Any permission prompt on record from the last two minutes counts as that click, not only the release's own.
- **Four operating modes.** `greenfield` builds something new. `bug_fix` reproduces a defect, fixes it minimally, and verifies once. `audit` reviews an existing codebase and produces findings rather than code. `research_publish` synthesizes sources into a paper plus an illustrative app, with every claim bound to a logged source.
- **A red-first stage loop with teeth.** A hook blocks edits to implementation files while a stage is open and the failing test has not yet been approved by a human. Tests come before code because the tooling will not permit the reverse.
- **The red gate protects its whole control set.** The role file, the stage marker and the hook itself are inside the gate, the 29 control-set Edit deny rules mirror the control list in `scripts/lib/hook-root.cjs`, and the hook keeps its own copy of that list, held to it by the kit's release tests.
- **Stage evidence a later reader can check.** Each stage's RED and GREEN runs, the gate's judgments and the release lane's result are records bound to the tested files, and `node scripts/evidence.cjs --stage <id> --verify` checks them against the tree.
- **Two drift checks on a stage's scope.** The scope compare: the RED release records the scope sections its stage prompt's refs name, as HEAD carried them at the release, and the amendment and stage-end publishes refuse when that text has changed, until a new release (deterministic enforcement over the recorded text); a ref's own refs are not followed, a section no ref names is outside the record, and a project with no Phase doc at HEAD records none. The changed-path check: the stage-end publish refuses a path changed since the approval's base that lies outside the stage's allowed set unless an `out-of-scope:` line in the packet names it (deterministic enforcement); it sees paths, never contents, and that line is the builder's own word (agent judgment).
- **Blind verification with a calibration gate.** Each milestone ends with a verifier session whose reading list structurally omits the builder's notes. Before its findings are counted, it must catch every defect in a seeded set, judged blind and scored by the orchestrator against sealed answers. A verifier that misses seeded defects is not trusted with real ones.
- **A spec that cannot be quietly edited.** The original spec is frozen at the bootstrap commit, the live spec changes only through approved change files recorded in a hash chain, and the commit floor, the file check and the closeout walk that chain (deterministic enforcement); a fresh-context challenge and your sign-off are recorded before the freeze.
- **A human-drive floor.** A Full-tier spec carries an in-real-life / human-in-the-loop plan - drive moments, what the human verifies by hand, where each answer gets typed - checked mechanically, and the milestone closeout consumes it: human-typed drive answers are required beside the closeout stamp before the closeout counts. An agent's recorded drive alone no longer satisfies the close.
- **Sessions that say what they are.** The session-start stamp identifies the session's role in plain words plus the checkout topology; the mode-setting script prints the launch order that prevents the shared-role-file race; a topology assist prints the worktree-split steps when the split is available and not yet taken.
- **Verification lanes over one registry.** `verify-local --lane fast|stage|release` - three filters over a single task registry, with `release` derived as the complete registry so omission is structurally impossible. Every run emits a deterministic JSON summary (verdicts, named skip reasons, durations in stated milliseconds, a registry hash). The bare invocation is the complete floor; `fast` and `stage` are developer feedback and are never release evidence.
- **An enforcement layer that is itself tested.** Validators and hooks guard the stage protocol, the retrospective stamp, test honesty, risk declarations, destructive operations, release readiness and spec-example coverage in your project, and this repository's own CI checks its entry documents for drift - and an enumeration check in CI proves each shipped validator is catalogued everywhere that lists them. A regression suite proves each check still fires; `sbak/scripts/bake-inheritance.cjs` ships as the effectiveness proof a reader can run.
- **Evidence you can read.** Sessions leave append-only event ledgers. A collector turns those plus committed history into a deterministic report bound to real commits, showing findings, fixes, and rework - with unknown values reported as unknown rather than as zero.
- **Reproducible, provenance-carrying artifacts.** The starter archive is built from a signed tag, never from a working tree. The same tag always produces the same hash. This release's artifacts are `sbak-v1.0.11-starter.zip` and, beside it, `sbak-install.cjs` - both attested.
- **Runs on a supported runtime.** CI and the generated workflows pin Node 24 (Active LTS), and a floor check derives the minimum Node the kit's own prescribed test form requires from the prescription itself - the pins and the prescription cannot silently diverge again.

## Limitations

The honest list. Every item here is a reason not to trust the kit further than it has earned:

- **The cost against a lighter loop is not measured on this release.** The trial that measured it ran on an earlier release, before the weight was cut; that result no longer describes the kit, and it is being re-run. The result will be published here.
- **No worked example ships in this release.** There is no end-to-end tutorial project you can read start to finish. `example-receipt.html` is a real build receipt of this kit's own history: the collectors read the commit it names (observed evidence), and the release build refuses an example that was not rendered from a clean tree at the release (deterministic enforcement). It is evidence of the process running, not a guided walkthrough.
- **No human security audit has been performed.** None is claimed. Build provenance stops at SLSA Level 2. Absence of a claim is not a claim of absence.
- **Verified on Windows and Linux; macOS is field use only.** Linux CI (`ubuntu-latest`, Node 24) is the authoritative verification environment and Windows (Node 22+, Git, PowerShell or Git Bash) the development floor; there is no platform matrix. Outside users have run builds on macOS, but no macOS verification run exists.
- **The overhead is real and sometimes not worth it.** For work that fits in an afternoon, or throwaway code, or a project no one will ever need to reconstruct, this kit costs more than it returns. `WHY-THIS-KIT.md` names the cases where you should not use it, and means them.
- **The static gate floors cover four language families** - JS/TS/JSX-TSX, Python, Go, and Rust. Anything else gets a visible skip line plus verifier-stage coverage. Disclosed, never silent, but a skip is a skip.
- **The permission fence is a fence, not a sandbox.** Its deny rules have known bypasses. Keep secrets off disk.
- **The shell write gate is a parser, not a sandbox.** Until the human approves a stage's failing tests, the gate refuses a shell command that writes an implementation file through a recognised write construct (a redirect, `tee`, `sed -i`, `cp`, `mv`, `truncate`, `node -e` or `node -p`, a PowerShell `Set-Content` or `Clear-Content`, and the others the hook lists), and one whose target it cannot read; in every state it refuses one that deletes, moves or writes one of its own control files, `git clean -x` and `git stash -a` among them. It reads a construct at any nesting it can parse, up to eight levels deep: inside `$(...)`, backticks and process substitutions, inside an unquoted heredoc body, an arithmetic expansion and a parameter expansion, after keywords such as `then` and `do`, inside PowerShell script blocks, and inside `bash -c`, `sh -c`, `zsh -c`, `eval`, `pwsh -c` and `powershell -Command` when their text is literal. A body nested deeper or never closed, a wrapper whose text is not literal, and a deletion whose target it cannot read (one that arrives on a PowerShell pipeline or through `xargs` among them) are refused while a stage is engaged (open, its failing tests not yet approved). It judges nothing else: a script or program that writes a file itself, an alias, an interpreter without a literal path in the command, `cmd /c`, `Invoke-Expression`, `env -S`, `find -exec`, `find -delete`, `ln` and `dd` are not judged, and a shell working folder carried over from an earlier command is not seen.
- **The gate's own scripts are held by their form and by the recorded prompt, not by who runs them.** The hook lets `approve-red.cjs` and `stage-active.cjs` run only in their bare forms, and from a Claude Code session the release, the void and the clear refuse unless the prompt the command raised is on record. From your own terminal, outside the session, they run with no recorded prompt, except under a test runner or a package script, or where the process tree cannot be read. Any prompt from the last two minutes counts, not only that command's, and the receipts file is one the session's own tools can write, so the record shows that a prompt was recorded, not who answered it. [docs/limitations.md](docs/limitations.md) has the detail.
- **The hook's reading of PowerShell is its own.** It follows PowerShell's written rules and is checked against real PowerShell on a corpus, but a form outside the corpus where the two readings differ can still hide a write to an ordinary file. One such form is known: a typographic dash (an en dash, an em dash or a horizontal bar) before a parameter name, which PowerShell reads as `-` and the hook does not. Judging such a command with PowerShell's own parser is planned for a later release. The gate's own names are judged by name, never by the reading. [docs/limitations.md](docs/limitations.md) has the detail.
- **The evidence records are checked against each other and the commit, never against their author.** Anyone who can write the repository can rewrite a record together with its manifest and `evidence.cjs --verify` still passes; a fabricated record is outside the local trust boundary the evidence path claims. The first evidence path supports one host (Claude Code at 2.1.295 or later), one test runner reading (`node --test`) and one transport; anything else is unsupported on this path.
- **The calibration seal is a check after the fact, not a file block.** A recorded read of an answer file voids the verifier's exam when the scorer runs with the verifier's `--session` or the verifier runs `--check verify`, but nothing stops the read, and a file outside the two answer folders that carries the answers (an earlier exam's findings, for example) is not refused. The exam is only as blind as the verifier's reads.
- **The spec chain proves where the live spec came from, not that a change was wise.** The commit floor checks the hashes and that a change names requirement ids the live spec defines; the approval and sign-off lines are text it checks for being filled, not for who wrote them; a change's contract text and named tests are not compared with the live spec; `git commit --no-verify` skips it; and it holds only in a project that carries the spec-chain validator. `docs/limitations.md` has the whole list.
- **Token cost is higher than a plain instruction file.** The kit caps per-session reading lists to keep this bounded, but a framework of this size costs more to run than a concise `CLAUDE.md`.
- **The human stamp is load-bearing.** Not by reading the code - by reading the agent's review and the orchestrator's comments and running any live testing before stamping. Rubber-stamp the stages and every control in the kit degrades to ceremony.
- **Pin a tag.** Releases are snapshots of a privately developed kit. Interfaces may still change between releases; pin the tag you verified.
- **Pull requests are not accepted.** Development is private and this is a snapshot. Issues are read; no response time is promised.

## Evidence

What backs the claims above, and how you can check it yourself:

- **Continuous integration runs seven checks of the kit's enforcement layer against the kit, on Node 24, on every pull request and every push to main:** the stage-prompt schema check over the shipped templates; the enumeration check proving each shipped validator is catalogued everywhere that lists them; the entry-doc drift check, including numeric self-description claims, at both levels; the seeded-defect calibration set, checked in both directions so no fixture leaks its own answer; the golden-scaffold manifest check and its contract diff, so a template edit cannot silently change what a bootstrapped project receives; and a bake harness that renders a real project, plants a violation, and requires the inherited validator to reject it (deterministic enforcement). It does not run the release verification lane. Presence is never taken for effectiveness.
- **The build receipt is real.** `example-receipt.html` is derived by the collectors from the commit it names: they read the repository's files at that commit, take a claim only from a structured field such as a `verdict:` line, and print UNKNOWN for the verdict, the controls count or the caught-and-fixed count when it has no such source; the milestones count reads 0 when no CHANGELOG entry, completion or release row exists (deterministic enforcement). Figures from session event ledgers, read from disk because they are never committed, cannot be re-derived from the repository (observed evidence of the session that rendered it). It is not a staged demonstration: intervals that are unknown are printed as unknown.
- **The GA decision record is executed, not asserted.** Every one of the five properties above was demonstrated by running the defect's attack shape against real artifacts - planted symlinks, torn writes, missing shells, drifted copies - and watching the control refuse, restore, or fail loudly. The transcripts of those runs are not part of this release; what you can check here is the CI record above and `example-receipt.html`.
- **This release's work was verified three ways, and one fix by none of them.** The previous release was walked feature by feature in five audit passes, each followed by a fresh-context challenge: 22 red findings, each closed by one of thirteen fix stages, RED-first, under the owner's stamp. The live spec was verified by two fresh-context verifier iterations: the first found two important gaps (the tier line switched the spec floor off; a change's requirement ids were not compared with the live spec), which a fix stage closed; the second found one more (the upgrade could start a chain in a project with no validator to check it), fixed in the closeout stage with its own failing tests first and a mutation. No third verifier iteration checked that last fix. The calibration exam was scored by the orchestrator, not the verifier, at 0 missed seeds in both iterations. The transcripts of those runs are not part of this release.
