# Release notes - v1.0.10

**This is the current GA release of the Software Build Assurance Kit: the gate attests itself.** The 1.0 bar is an integrity bar, not a feature bar: five decision-record properties, each demonstrated absent-of-defect **by execution** on verifier-built fixtures, in the authoritative CI environment. The evidence trail for every claim below is public in this repository's checks and in `example-receipt.html`.

Read this page before you adopt the kit for anything you care about. It says what works, what does not, and what evidence backs each claim. The release history in the same shape is in [CHANGELOG.md](CHANGELOG.md).

## What v1.0.10 changes

The gate attests itself. A stage's acceptance now leaves records a later reader can check, the verifier's calibration exam is scored by someone other than the verifier, and the gate's own scripts and its reading of PowerShell are held more tightly. Where the kit used to ask a person or an agent to remember a step, a program now does the step or refuses. The build loop does not change, and the Claude Code floor stays at 2.1.295.

- **Each stage's evidence is a record.** The RED run and the GREEN run are written under the stage's `.claude/evidence/<stage>/` folder, each bound to a fingerprint of the files it tested, beside the gate's judgments, the channel's refusals, the release lane's result and the stage's lifecycle. The release refuses a RED record that passed or that names other files than the ones approved, and the stage end, the pre-commit check and the push check read the records against the tree (deterministic enforcement over observed evidence). The orchestrator reviews them with a fixed procedure before it asks for the stamp (agent judgment).
- **The verifier's exam is scored by someone else.** The verifier judges the seeded-defect set blind and writes verdicts only; the orchestrator scores them against the sealed answers with `node scripts/calibration-score.cjs`. A recorded read of an answer file voids the exam. That check runs on the session's read record after the fact; it is not a file-access block (see Limitations).
- **The gate's own scripts run only as asked.** `approve-red.cjs` and `stage-active.cjs` run only in their bare forms, and from a Claude Code session the release, the void and the clear refuse unless the permission prompt the command raised is on record (deterministic enforcement over the session's receipts).
- **The PowerShell tool is read as PowerShell reads it.** Under Claude Code's PowerShell tool the hook follows PowerShell's quoting, comment and grouping rules, treats `>` as a redirect wherever PowerShell starts a token, reads the stop-parsing token's line as literal text that it still judges, and refuses a command that names a gate script or a control file unless it is a bare form. Where `pwsh` is installed, real PowerShell checks that reading on a corpus. It is still the hook's own reading; the limitations below name the form it is known to miss.
- **What used to be remembered, a program now does.**
  - The orchestrator sends its ordinary messages on its own authority; only the release still needs the owner's `/send --approval` and the click.
  - A stage opens only while the orchestrator listens, with a live channel watcher; a recent prompt in its window no longer counts, and the builder arms its own watcher.
  - `kit-update --ready --model <model>` prints the leaving-bootstrap block itself, filled from the project, so the bootstrap never composes it.
  - The installer says before the download whether `gh` can check the build attestation: signed in, not found, or not signed in.
  - A channel message that is not valid UTF-8 is refused before anything is written, and a stage-open already on the log stands instead of failing.
- **An upgrade keeps your CLAUDE.md.** A CLAUDE.md the kit placed for you is kept as yours on every upgrade.

### Upgrading a v1.0.9 project

Run the same command as the install: download this release's `sbak-install.cjs` into the project folder, start `claude` there, type `sbak-install`, and answer `upgrade`. Then run `node scripts/kit-update.cjs --migrate`: the table first, then `--apply-all` to write.

One setting is yours to change. An upgrade never removes a rule you have, so the old ask rule on every orchestrator send stays and still asks for a click on each one. To keep the click on the release only, replace `Bash(node scripts/channel.cjs send *)` in the ask list of a staged copy of `.claude/settings.json` with `Bash(node scripts/channel.cjs send --approval*)` and `Bash(node scripts/channel.cjs send * --approval*)`, then place it with `node scripts/kit-update.cjs --place-settings <staged copy>`. The hand-applied path for the rest is in the [CHANGELOG](https://github.com/kknipe2k/Software-Build-Assurance-Kit/blob/main/CHANGELOG.md) under "Manual change for a v1.0.9 project".

### Carried from the previous release, unchanged

The previous release's work, what breaks stops instead of allowing:

- **The gate fails closed on its own faults.** The red gate works out one of three states before it judges anything, and in the unknown state it refuses every edit and command with the fault and one recovery line.
- **The shell write gate, and what it is not.** Until the human approves a stage's failing tests, the gate refuses a shell command that writes an implementation file through a recognised write construct, and one whose target it cannot read. It is a parser, not a sandbox.
- **An approval that stops standing is void.** `/approve-red` refuses without its evidence and records what it released; an implementation edit is refused once an approved test file changes with no orchestrator ack.
- **Four attestation outcomes, and rejection stops.** Verified, unavailable, could not run, or REJECTED; a rejected asset installs nothing.
- **One readiness result.** `kit-update --ready` prints one line per check and one next command, reads the three markers the way the hook's probe does (a one-line approval marker beside a v2 approval record, which the hook reads as unknown, is not among them), and an upgrade ends on the same block.
- **The settings file has one door.** `node scripts/kit-update.cjs --place-settings <filled-file>` checks the kit's hook registrations and permissions first and keeps the old bytes.

## What GA means here

The GA decision record required, and independent verification confirmed by execution:

1. **Adoption never mutates outside the project root** - symlink escapes (external, internal, dangling) are refused at every install site, targets byte-untouched, loudly and non-zero.
2. **Adoption never reports success with controls dormant** - hook wiredness is parsed, not pattern-matched; a fresh session proves the read-first stamp before success is claimed.
3. **The release verification lane has no silent or required skip** - every task appears in the run's own machine-readable summary with a verdict; a required skip is a failure, never a pass.
4. **POSIX hook liveness is proven, not assumed** - rendered hooks execute on Linux CI with the executable bit asserted; a Windows-local green is disclosed as non-authoritative at the point of use.
5. **A failed settings merge cannot destroy user settings** - byte-exact archive, atomic replace, auto-restore proven on a planted mid-write failure; unparseable settings are never replaced.

Each was verified twice: by the framework's own gates, and by an independent fresh-context verifier session that built its own fixtures and reproduced the release lane in a pristine clone.

## Capabilities

- **A bootstrap that asks what you are building and derives the rest.** It infers the operating mode from your description, derives the risk posture from the spec, and shows the calibration as one acceptance line. Everything else is derived by a script from a single authority file and surfaced with its one-line why.
- **One-file install and upgrade.** `sbak-install.cjs`, attested beside the ZIP, drives the whole install from inside `claude` - checksum and attestation verified, blast radius disclosed, its questions one step at a time, nothing written before your word - and upgrades an installed kit the same way, keeping what you modified and naming the bootstrap-filled files it leaves at the installed version.
- **A channel between the two terminals.** Stage packets and verdicts travel between the orchestrator and the builder over an append-only log with automatic pickup - `/listen` puts a session on watch, and the orchestrator's messages leave on its own authority - and the verifier and refactorer sessions use it too; the release remains the human's keystroke and click.
- **Four operating modes.** `greenfield` builds something new. `bug_fix` reproduces a defect, fixes it minimally, and verifies once. `audit` reviews an existing codebase and produces findings rather than code. `research_publish` synthesizes sources into a paper plus an illustrative app, with every claim bound to a logged source.
- **A red-first stage loop with teeth.** A hook blocks edits to implementation files while a stage is open and the failing test has not yet been approved by a human. Tests come before code because the tooling will not permit the reverse.
- **The red gate protects its whole control set.** The role file, the stage marker and the hook itself are inside the gate, the ten control-set Edit deny rules mirror the control list in `scripts/lib/hook-root.cjs`, and the hook keeps its own copy of that list, held to it by the kit's release tests.
- **Stage evidence a later reader can check.** Each stage's RED and GREEN runs, the gate's judgments and the release lane's result are records bound to the tested files, and `node scripts/evidence.cjs --stage <id> --verify` checks them against the tree.
- **Blind verification with a calibration gate.** Each milestone ends with a verifier session whose reading list structurally omits the builder's notes. Before its findings are counted, it must catch every defect in a seeded set, judged blind and scored by the orchestrator against sealed answers. A verifier that misses seeded defects is not trusted with real ones.
- **A human-drive floor.** A Full-tier spec carries an in-real-life / human-in-the-loop plan - drive moments, what the human verifies by hand, where each answer gets typed - checked mechanically, and the milestone closeout consumes it: human-typed drive answers are required beside the closeout stamp before the closeout counts. An agent's recorded drive alone no longer satisfies the close.
- **Sessions that say what they are.** The session-start stamp identifies the session's role in plain words plus the checkout topology; the mode-setting script prints the launch order that prevents the shared-role-file race; a topology assist prints the worktree-split steps when the split is available and not yet taken.
- **Verification lanes over one registry.** `verify-local --lane fast|stage|release` - three filters over a single task registry, with `release` derived as the complete registry so omission is structurally impossible. Every run emits a deterministic JSON summary (verdicts, named skip reasons, durations in stated milliseconds, a registry hash). The bare invocation is the complete floor; `fast` and `stage` are developer feedback and are never release evidence.
- **An enforcement layer that is itself tested.** Validators and hooks guard the stage protocol, the retrospective stamp, test honesty, risk declarations, destructive operations, release readiness and spec-example coverage in your project, and this repository's own CI checks its entry documents for drift - and an enumeration check in CI proves each shipped validator is catalogued everywhere that lists them. A regression suite proves each check still fires; `sbak/scripts/bake-inheritance.cjs` ships as the effectiveness proof a reader can run.
- **Evidence you can read.** Sessions leave append-only event ledgers. A collector turns those plus committed history into a deterministic report bound to real commits, showing findings, fixes, and rework - with unknown values reported as unknown rather than as zero.
- **Reproducible, provenance-carrying artifacts.** The starter archive is built from a signed tag, never from a working tree. The same tag always produces the same hash. This release's artifacts are `sbak-v1.0.10-starter.zip` and, beside it, `sbak-install.cjs` - both attested.
- **Runs on a supported runtime.** CI and the generated workflows pin Node 24 (Active LTS), and a floor check derives the minimum Node the kit's own prescribed test form requires from the prescription itself - the pins and the prescription cannot silently diverge again.

## Limitations

The honest list. Every item here is a reason not to trust the kit further than it has earned:

- **The cost against a lighter loop is not measured on this release.** The trial that measured it ran on an earlier release, before the weight was cut; that result no longer describes the kit, and it is being re-run. The result will be published here.
- **No worked example ships in this release.** There is no end-to-end tutorial project you can read start to finish. `example-receipt.html` is real - derived from the source repository's actual commits, findings, and rework - but it is evidence of the process running, not a guided walkthrough.
- **No human security audit has been performed.** None is claimed. Build provenance stops at SLSA Level 2. Absence of a claim is not a claim of absence.
- **Verified on Windows and Linux; macOS is field use only.** Linux CI (`ubuntu-latest`, Node 24) is the authoritative verification environment and Windows (Node 22+, Git, PowerShell or Git Bash) the development floor; there is no platform matrix. Outside users have run builds on macOS, but no macOS verification run exists.
- **The overhead is real and sometimes not worth it.** For work that fits in an afternoon, or throwaway code, or a project no one will ever need to reconstruct, this kit costs more than it returns. `WHY-THIS-KIT.md` names the cases where you should not use it, and means them.
- **The static gate floors cover four language families** - JS/TS/JSX-TSX, Python, Go, and Rust. Anything else gets a visible skip line plus verifier-stage coverage. Disclosed, never silent, but a skip is a skip.
- **The permission fence is a fence, not a sandbox.** Its deny rules have known bypasses. Keep secrets off disk.
- **The shell write gate is a parser, not a sandbox.** Until the human approves a stage's failing tests, the gate refuses a shell command that writes an implementation file through a recognised write construct (a redirect, `tee`, `sed -i`, `cp`, `mv`, `truncate`, `node -e` or `node -p`, a PowerShell `Set-Content` or `Clear-Content`, and the others the hook lists), and one whose target it cannot read; in every state it refuses one that deletes, moves or writes one of its own control files, `git clean -x` and `git stash -a` among them. It reads a construct at any nesting it can parse, up to eight levels deep: inside `$(...)`, backticks and process substitutions, inside an unquoted heredoc body, an arithmetic expansion and a parameter expansion, after keywords such as `then` and `do`, inside PowerShell script blocks, and inside `bash -c`, `sh -c`, `zsh -c`, `eval`, `pwsh -c` and `powershell -Command` when their text is literal. A body nested deeper or never closed, a wrapper whose text is not literal, and a deletion whose target it cannot read (one that arrives on a PowerShell pipeline or through `xargs` among them) are refused while a stage is engaged (open, its failing tests not yet approved). It judges nothing else: a script or program that writes a file itself, an alias, an interpreter without a literal path in the command, `cmd /c`, `Invoke-Expression`, `env -S`, `find -exec`, `find -delete`, `ln` and `dd` are not judged, and a shell working folder carried over from an earlier command is not seen.
- **The gate's own scripts are held by their form and by the recorded prompt, not by who runs them.** The hook lets `approve-red.cjs` and `stage-active.cjs` run only in their bare forms, and from a Claude Code session the release, the void and the clear refuse unless the prompt the command raised is on record. From your own shell, outside the session, they run with no recorded prompt. Any prompt from the last two minutes counts, not only that command's, and the receipts file is one the session's own tools can write, so the record shows that a prompt was recorded, not who answered it. [docs/limitations.md](docs/limitations.md) has the detail.
- **The hook's reading of PowerShell is its own.** It follows PowerShell's written rules and is checked against real PowerShell on a corpus, but a form outside the corpus where the two readings differ can still hide a write to an ordinary file. One such form is known: a typographic dash (an en dash, an em dash or a horizontal bar) before a parameter name, which PowerShell reads as `-` and the hook does not. Judging such a command with PowerShell's own parser is planned for a later release. The gate's own names are judged by name, never by the reading. [docs/limitations.md](docs/limitations.md) has the detail.
- **The evidence records are checked against each other and the commit, never against their author.** Anyone who can write the repository can rewrite a record together with its manifest and `evidence.cjs --verify` still passes; a fabricated record is outside the local trust boundary the evidence path claims. The first evidence path supports one host (Claude Code at 2.1.295 or later), one test runner reading (`node --test`) and one transport; anything else is unsupported on this path.
- **The calibration seal is a check after the fact, not a file block.** A recorded read of an answer file voids the verifier's exam, but nothing stops the read, and a file outside the answer folder that carries the answers (an earlier exam's findings, for example) is not refused. The exam is only as blind as the verifier's reads.
- **Token cost is higher than a plain instruction file.** The kit caps per-session reading lists to keep this bounded, but a framework of this size costs more to run than a concise `CLAUDE.md`.
- **The human stamp is load-bearing.** Not by reading the code - by reading the agent's review and the orchestrator's comments and running any live testing before stamping. Rubber-stamp the stages and every control in the kit degrades to ceremony.
- **Pin a tag.** Releases are snapshots of a privately developed kit. Interfaces may still change between releases; pin the tag you verified.
- **Pull requests are not accepted.** Development is private and this is a snapshot. Issues are read; no response time is promised.

## Evidence

What backs the claims above, and how you can check it yourself:

- **Continuous integration runs the kit's enforcement layer against the kit, on the pinned runtime.** On every push and pull request: the stage-prompt schema check over every phase document; the enumeration check proving each shipped validator is catalogued everywhere that lists them; the seeded-defect calibration set, checked in both directions so no fixture leaks its own answer; the entry-doc drift engine, including numeric self-description claims; the golden-scaffold check, so a template edit cannot silently change what a bootstrapped project receives; a bake harness that renders a real project, plants a violation, and requires the inherited validator to reject it; and the complete release verification lane with its machine-readable summary. Presence is never taken for effectiveness.
- **The build receipt is real.** `example-receipt.html` is derived by the collectors from this repository's own commits, findings, and rework. It is not a staged demonstration and it does not hide its gaps: intervals that are unknown are printed as unknown.
- **The GA decision record is executed, not asserted.** Every one of the five properties above was demonstrated by running the defect's attack shape against real artifacts - planted symlinks, torn writes, missing shells, drifted copies - and watching the control refuse, restore, or fail loudly. The transcripts of those runs are not part of this release; what you can check here is the CI record above and `example-receipt.html`.
- **This release's work was verified six times.** Six fresh-context verifier iterations: 16 red findings over the first five, each closed by a fix stage and re-proven by execution, and one in the sixth (a pin gap; the code sound), closed by pins proven on the verifier's own plant; 17 in all. The calibration exam was scored by the orchestrator, not the verifier, at 0 missed seeds in every iteration. The transcripts of those runs are not part of this release.
