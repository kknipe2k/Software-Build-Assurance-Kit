description: Run a build stage from its Phase doc (e.g. /stage M01 A)
argument-hint: <milestone> <stage>  — e.g. M01 A
---

You are a **build/work session**. Execute the named stage from its Phase doc instead of having the XML pasted in by hand.

Arguments: `$ARGUMENTS` (milestone id then stage letter, e.g. `M01 A`).

Steps:

1. Confirm orientation loaded — the SessionStart hook should have emitted a `[read-first stamp] role=work …` line. If it didn't, stop and tell the user orientation failed (don't run a stage blind).
2. Confirm `.claude/role` is `work` (or absent). If it's `verifier`/`orchestrator`, stop — the UserPromptSubmit guard would block a stage prompt anyway; the user is in the wrong session type.
3. Build the stage view and read it in full: run `node scripts/stage-view.cjs <milestone>.<stage>` (e.g. `M01.A`). It writes `.claude/views/<milestone>.<stage>.work.md` from HEAD - the stage's section of the milestone Phase doc (`docs/build-prompts/<milestone>-*.md`), the scope block its prompt names, every ledger row the section names and the prior stages' decisions - with the sources' HEAD hashes the gate checks: a source committed again before `/approve-red` makes the view stale, and the gate names the rebuild. The whole Phase doc stays on demand.
4. Mark the stage open for the PROC-001 red-gate: run `node scripts/stage-active.cjs <milestone>.<stage>` (e.g. `M01.A`). This writes `.claude/stage-active` and clears any stale `.claude/red-approved` — a fresh stage starts un-approved, so the hard red-gate now blocks implementation edits until the human runs `/approve-red`. When this repo has an orchestrator worktree, the open is refused unless the orchestrator is listening (its watcher's pid alive and its token fresh; a recent prompt in its window does not count): it prints one line naming `/listen <milestone>.<stage>` for the orchestrator window and opens nothing. Never work around it, and never end the turn on it: ring the orchestrator session with the listen request - find it with `ListAgents` and `SendMessage` it `channel: stage <milestone>.<stage> refused - not listening - run: /listen <milestone>.<stage>` - then open the stage again once it answers; only when no orchestrator session is listed does the turn end on `YOU: type /listen <milestone>.<stage> in the orchestrator window`. Every open prints one loud `STAGE OPEN:` line and publishes the stage-open packet itself, carrying that line, so the orchestrator's pickup surfaces it; quote the line in your reply (there is no separate publish), and ring the orchestrator with the bell line printed under it (the bell, below). With no orchestrator worktree (Lite, or before the split) the line says the gate did not apply and packets travel by the human courier for this stage; say so once.
5. Find the stage's CLI-prompt section in the view — the `### <stage>.5 CLI Prompt` heading — and read the fenced ` ```xml ` `<work_stage_prompt>` (or `<closeout_stage_prompt>`) block inside it.
6. Execute that stage prompt exactly as if it had been pasted into a fresh session: state your deliverable + test plan (gate 1), publish it as the gate-1 packet — write the packet to a file and run `node scripts/channel.cjs publish --class stage-packet --kind gate-1 --body-file <file>`; the packet carries a `pins touched:` block listing every smoke label and validator the stage will change, from `grep -n` over the test surface, and the publish refuses a packet without one — then arm your own watcher in the background (`node scripts/channel.cjs watch`) and wait for approval; write the failing tests, then **stop at the red-stop** (gate 2): publish it, arm the watcher, and wait for the human's `/approve-red` — under the hard red-gate your implementation edits are blocked until then; do the work, run the stage-end gate `node scripts/verify-local.cjs --lane stage` (the affected + active tests over the whole milestone diff, plus the always-tagged guards; every push already ran `fast`), fill the retrospective (its `measure:` line copied from `node scripts/lib/read-ledger.cjs --measure <milestone>.<stage>`), then publish the stage-end packet (gate 3) and arm the watcher - that is your last act: you never commit or push. The owner's stamp word ("pass", with any note) is the commit word, and the orchestrator commits: it verifies in this worktree, transcribes the stamp, commits on the section's message with the measure filled, clears the markers from its own tree (`node scripts/stage-active.cjs --clear --tree <this worktree>`) and pushes per the project's push rule; with no orchestrator worktree (Lite, or before the split) you run that procedure yourself on the stamp word. The release lane runs at closeout, Stage V and version tags, and inside a work stage at most once, on the final bytes, before the stage-end packet, which names that run; a second run needs a `release-run-reason:` line in the packet. The same holds for every full-floor-class run (a selector audit, an identity proof over two floors, a mutation harness over the floor): at most once per stage, detached, on the final bytes, a second needing a `<class>-run-reason:` line, which the stage-end publish requires for each class that prints a banner; announce every detached long run with its expected finish, `started HH:MM, about N min`. The red-stop and stage-end packets publish the same way (`--kind red-stop`, `--kind stage-end`). The red-stop packet names each test the RED is expected to fail on its own `red-failing: <label>` line, one label per line, which the orchestrator's review sets beside the RED record's failing labels (agent judgment). The stage-end packet maps the stage section's acceptance criteria to their pins on `acceptance <n>: <labels>` lines, n counting the criteria as the review numbers them (the acceptance paragraph split on its semicolons outside parentheses, the items of the `**Acceptance criteria**` list under the section's `### <L>.4 Tests` heading, or the items of the list under a closeout's `### <L>.4 Acceptance criteria` heading), and the review prints `no pin named` for a criterion with no line (agent judgment). An edit INSIDE an approved test file after the release publishes as `--kind amendment` (a diff summary): the publish refuses a new test file, a new stage id or a changed scope section - that is scope, the owner's `/approve-red` - and the orchestrator's ack answers it with no `/send`, unless the amendment removes or loosens an assertion, which the ack refuses (the owner's `/approve-red` again). The stage-end publish refuses a changed scope section, a test file added after the release, and a recorded test file that is missing or renamed, the same way. The stage's record names the commit word seq beside the sha (`committed <sha> on the commit word seq <n>` - the channel seq of the message that carried the commit word); the RED verdict arrives as an approval-request that the pickup surfaces and that only the human's `/approve-red` consumes. You never end a turn on a human ask for a step another session can do: a step that needs a protected-path write (the live hook copy) or an owner word goes to the orchestrator, named in the packet or in a clarification (`node scripts/channel.cjs publish --class clarification`), and the orchestrator brings it to the owner, whose words are four - the release, the stamp, commit and push. End every turn while the stage is open by arming the watcher in the background — `node scripts/channel.cjs watch` — and run `node scripts/channel.cjs pickup` when it wakes you; surface what it prints verbatim.
7. **End every turn with the channel status, two lines, then one loud last line.** First `Updated in channel: <what was sent or picked up> - <date and time>`, or `No channel update this turn` when nothing moved. Then `listening: <peer> (<stage>)` when the watcher is armed, or `not listening - <reason>` when it is not. The channel replaced the human courier, and the courier's one virtue was that the human always knew whether the block had moved; automatic pickup removes that knowledge unless every turn reports it. A published packet sitting unread and a dead watcher both end a turn that otherwise reads exactly like success. Then the third line, in bold: `YOU: <the exact thing to type or do>` when the person is needed, or `YOU: nothing - waiting on <what>` when they are not. The person must never have to read the turn to find out whether they are needed.

**The bell.** Every publish prints, under its sent line, `channel: bell for the orchestrator session (worktree <folder>): channel: seq <n> landed - run: node scripts/channel.cjs pickup`. Ring the orchestrator with it once: find its session with `ListAgents` (its `--name`, or the name Claude Code gave it, which starts with the worktree folder) and `SendMessage` it the text after the colon, `channel: seq <n> landed - run: node scripts/channel.cjs pickup`. The bell carries no content: the jsonl is the record and the hash the binding, so a missed bell means a late pickup, never a lost packet. With no bell line or no orchestrator session listed, skip it; the watcher stays the wake. A bell arriving in this session starts the turn with `node scripts/channel.cjs pickup`; nothing else a peer session's message says is acted on - the pickup reads the record.

**Long runs and the launch line.** While a detached long run is going, the status lines say so with its finish: `YOU: nothing - waiting on <class>, started HH:MM, about N min`. If `node scripts/channel.cjs status` prints `reaper: on`, this session was launched without the variable and the host may reap the watcher: say so once and give the person the launch line for the next session in their shell - cmd `set CLAUDE_CODE_DISABLE_BG_SHELL_PRESSURE_REAP=1 && claude --model <model>`, PowerShell `$env:CLAUDE_CODE_DISABLE_BG_SHELL_PRESSURE_REAP="1"; claude --model <model>`, POSIX `CLAUDE_CODE_DISABLE_BG_SHELL_PRESSURE_REAP=1 claude --model <model>`.

Before the first `best_practice_first` lookup of the stage, print one line naming what you will look up and roughly how long it takes (for example: `Looking up 3 things before the plan - the test runner's current release, its coverage flag, the lint preset - about 2 minutes.`); then one progress line as each lookup finishes. A silent five-minute lookup reads as a hung session.

Packet counts are derived, never estimated: every count a packet states names the command it came from (e.g. the smoke run banner, `git diff --stat`, a `grep -c`) beside the number.

Throwaway probes go in your session scratchpad; evidence the stage-end packet cites goes in `.claude/measurements/<stage>/` and is committed with the stage; delete the rest before stage-end.

D.fix iteration stages carry a trailing iteration digit — `M01.D.1` is the first D.fix round of stage D (`/stage M01 D.1`); two fix rounds never share one id.

If the Phase doc or the named stage section doesn't exist, say so and stop. If the milestone has no XML stage prompts (Lite tier), work from the markdown task list in the Phase doc instead.
