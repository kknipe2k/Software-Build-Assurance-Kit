description: Run the Verifier (Stage V) for a milestone (e.g. /verify M01)
argument-hint: <milestone>  — e.g. M01

You are a **verifier session** — fresh-context, bias-guarded. Before doing anything, ensure `.claude/role` is `verifier` so the right read-first list loaded (the verifier list deliberately omits prior retrospectives). If the orientation stamp shows `role=work`, stop and tell the user to set verifier mode (`node scripts/set-mode.cjs verifier`) and reopen the session — running the Verifier with the work orientation defeats the bias guard.

> Always set the mode with `node scripts/set-mode.cjs <token>`, never a shell redirect. The script writes a temp file then atomically renames it over `.claude/role`, so a hook reading concurrently can never observe a half-written/empty file (the truncate-then-write race, ERR-002). `.claude/role` is canonical **bare-token** state: the strict reader accepts only an exact token; an absent file means `work`, and anything present-but-non-canonical fails closed (the prompt is blocked / the SessionStart stamp reads `role=unresolved`), never silently `work`.

Arguments: `$ARGUMENTS` (the milestone id, e.g. `M01`).

Steps:

1. Read every read-first entry tagged `when: verify` (the manifest in your stamp names them), then run `node scripts/lib/read-ledger.cjs --check verify` - it refuses, naming the file, if a required read is not on the ledger. Then open the milestone Phase doc `proposals/<milestone>-*.md (WORKSHOP-LOCAL: the kit repo keeps its milestone Phase docs in proposals/, e.g. proposals/M22-UAT-HARDENING.md)` and find its Stage V section — the `<verifier_stage_prompt>` block. Then publish the stage-open message so the orchestrator goes on listen, exactly as `/stage` does: `node scripts/channel.cjs publish --class stage-open --body <milestone>.V` (if it reports no channel - before the worktree split - the findings travel by the human courier; say so once).
2. Run the full floor first: `node scripts/verify-local.cjs --lane release` — Stage V is the adversary and runs the whole suite; "tests passed" in a `fast` lane is not Stage-V evidence. Then run the verification passes named there at the project's `verifier_mode` (default Full `pass_2_4` = hooks + behavior + security + code_quality — **no inventory pass** (§X.2 is advisory at the default); add `design` when `deliverable_type: web`; `pass_1_2_3_4` (explicit choice) adds inventory + multi-call; Lite `pass_1_only`). For `deliverable_type: web`, Pass 4 requires a literal observed-running step and Pass 5 the design-conformance check against `docs/design.md`.
3. Write findings to the findings file using `templates/VERIFIER-FINDINGS-TEMPLATE.md (WORKSHOP-LOCAL: the kit repo keeps its templates in templates/; generated projects render them to prompts/)`, including the mandatory tier-coverage caveat. At surface time publish the findings file as a stage-packet - `node scripts/channel.cjs publish --class stage-packet --kind verify-findings --body-file <findings file>` - and end the turn by arming the watcher in the background: `node scripts/channel.cjs watch`. The orchestrator's verdict arrives as a courier message; run `node scripts/channel.cjs pickup` when the watcher wakes you and surface what it prints verbatim. Approvals are unchanged.
4. Do **not** fix anything — the Verifier produces findings; remediation is the build session's job via the D.fix loop.
