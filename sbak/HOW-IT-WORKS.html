SOFTWARE BUILD ASSURANCE KIT

How It Works

A drop-in framework that turns a coding agent into a disciplined building partner. You describe what to build; it calibrates how much process to apply, then runs a structured loop with human approval gates, fresh-context verification, and an append-only audit trail.

What it does, in one picture

1 · DROP IN
Unzip the release ZIP, run adopt
The adopt step arms the Git hooks and verifies itself: exit 0 means every enforcement layer is active. Then open the folder in your agent.
2 · CALIBRATE
Answer one question
Full or Custom. Full (the default) infers the kind of work from what you say you are building and derives the risk posture from the spec, shown as one acceptance line; Custom asks three short questions. Sets how much ceremony and which gates apply.
3 · BOOTSTRAP
Spec, milestones, scaffold
Generates 52 files for Lite, 119 for Full (this tree's own derived figures). Then hands off to the build loop.
4 · BUILD LOOP
Stages, verified, approved
Each milestone runs as stages behind three human approval gates. No commit without your approval.
5 · SHIP
PR per milestone
Code, retrospectives, audit ledger, and the build receipt reviewed together, then merged.

The core promise: human reviews, agent implements, hooks and CI enforce. The agent never commits without your explicit approval. That rule holds in every tier and every mode.

Step 2 - Calibration (one question: Full or Custom)

The first thing the framework asks. On Full (the default) nothing in the table below is asked: the operating mode is inferred from what you say you are building, the tier is Full, and the risk triggers derive from the spec - all shown back as one acceptance line you press enter on. On Custom the three questions below are asked, plus a confirmation turn. Either way each value maps to settings stored in project-config.md; everything not asked is derived and confirmed back to you in plain English. You can change them later via an append-only override log.

QuestionOptionsWhat it controls
What kind of work is this? (asked) greenfield · bug_fix · research_publish · audit The operating mode: which discovery questions follow and the top-level shape of the work.
How much assurance? (asked) Full (default) Lite The tier: how much ceremony. Scaffold size, retrospective depth, validator severity (Full blocks, Lite warns).
Any risky surfaces? (asked) destructive data ops · archives · untrusted writes · credentials · untrusted HTML · installers The risk triggers. Risk overrides tier: each declared surface gets deeper verification, and at Full it arms CI enforcement of the append-only ledgers. This is the risk escalation path.
Deliverable type (derived + confirmed) CLI · Web-UI · Library · Service · Other The deliverable_type, orthogonal to tier. Decides which gates apply: web turns on a design brief (docs/design.md) plus browser-load and design-conformance verifier passes; library adds an API-surface contract; service adds endpoint contracts; cli adds command-surface checks. Usually inferred from your description rather than asked outright.
Verification & CI cost (derived + confirmed) Local-first · Cloud · Local-only The verification_locus: where the test suite runs and what GitHub Actions costs. Public repo: cloud is free and unlimited. Private repo: local-first (hybrid) keeps hosted minutes near zero. Orthogonal to tier; usually proposed from repo visibility and whether the project ships to macOS.

Don't know? The default is greenfield + Full, no declared risk (everything else derived and confirmed). Re-tiering later is cheap and tracked.

Three human approval gates, every work stage

GATE 1 · PLAN
Plan approval
The agent states its deliverable and test plan and waits. No work before you approve the plan.
GATE 2 · RED
The red gate
The agent writes failing tests first and stops. A hook blocks implementation edits until you review the failing tests and approve them. This stops tests being written to fit code that already exists.
GATE 3 · STAGE END
Stage-end approval
Implementation done, gates green, retrospective filled: the agent surfaces the diff and waits. No commit without your approval, and pushes are your call too.

Stages A-D - Work

  • Test-driven: failing tests first (the red gate above), then implementation, then green gates
  • All quality gates green; no skips, no --no-verify
  • The agent surfaces the diff and the retrospective at stage end
  • No commit until you approve. Then a fresh session opens for the next stage.

Stage V - Verifier

  • Fresh session with prior retrospectives deliberately hidden: the bias guard
  • Asks "does the code do what was promised?" not "did the tests pass?"
  • Full runs four passes by default: hooks (every wire claim traced from source to consumer), behavior (the running thing observed, not just the suite), security, and code quality. Lite runs the inventory pass only.
  • Every Verifier stage also runs a required plan-challenge pass: what dangerous properties did the plan and its acceptance criteria leave unproven?
  • Findings graded blocks merge · carry forward · tech-debt

Stage R - Refactorer (the refactor decision)

  • Checked at every milestone boundary, after the Verifier: Stage R runs when the tech-debt ledger reaches the threshold count OR the milestone interval elapses, whichever comes first
  • Asks "is the code maintainable?": duplication, complexity, drift, assessed against the cumulative codebase
  • Fresh session under the strictest bias guard: prior retrospectives AND prior R findings both hidden
  • A critical structural finding opens a scoped D.refactor stage; the Verifier re-runs first (the refactor broke no contracts), then Stage R re-runs. That second run is the post-refactor verification. Capped at 2 rounds per milestone.
  • Lite skips Stage R (refactor_mode: skip)

Stage E - Closeout

  • Cumulative review of everything shipped this milestone vs. the spec
  • Writes one entry in the append-only gap-analysis ledger (Full): never edited, only appended; CI enforcement arms when a risk trigger is declared
  • You review three artifacts together: the code diff, the retrospectives, and the ledger entry

The build receipt (receipt generation)

  • Every session leaves an event ledger under .claude/receipts/: a session hook records stage lifecycle events as they happen
  • node scripts/build-receipts.cjs render folds those ledgers and the committed history into a deterministic build receipt (JSON, HTML, and Markdown) under reports/
  • What it looks like on real work: example-receipt.html, generated from this kit's own build, never hand-edited

The two truths this picture carries: the session types never share a context, and you carry the surfaces between them (the conduit pattern). On this host the mode split is structural, not honor-system: the role guard is a hook. Each role's card follows below.

Orchestrator

  • Plans and routes: authors Phase docs, ADRs, protocol docs
  • Adjudicates the builder's gate surfaces; routes Verifier findings
  • Never edits code

Builder

  • Executes one stage per fresh session from a pasted prompt
  • Writes the failing tests first; the red gate holds until a human approves them
  • Does not sequence, route, or author Phase docs

Verifier

  • Starts blind: it structurally cannot see the builder's notes
  • Verifies the promise, not the tests; findings graded by severity
  • Calibrated: it must catch seeded defects before its findings count

Refactorer

  • Runs at milestone boundaries when the trigger fires (Stage R above)
  • Reads under the strictest bias guard of the four
  • Appends its findings to the tech-debt ledger

What is enforced, where

Three enforcement layers back the process. The session layer is the deepest and is specific to Claude Code; the Git hooks and CI are mechanical on any host, for any agent, once the adopt step has armed them.

LayerWhat it doesWhere it runs
Session layer Four session hooks: orientation auto-load with a verifiable stamp at session start, the role guard on every prompt, the red gate on implementation edits, and the receipts event recorder. Claude Code only. Other hosts (for example GitHub Copilot) never run these hooks; there the same steps are honor-system procedure that host's QUICKSTART teaches, and picking a Claude model inside another host does not change that.
Git hooks Pre-commit runs the validators over what is staged; pre-push runs the verification floor before anything leaves your machine. Any host, mechanically, once --adopt has armed them via core.hooksPath. They run no matter what wrote the commit.
CI Pull-request checks (smoke run, stage-prompt validation) and, when a risk trigger armed it, enforcement of the append-only ledgers. Any host: GitHub Actions, independent of the agent entirely.

Commit and push boundaries, every host: the agent never commits and never pushes without your explicit approval. The session layer enforces the discipline around that promise where it runs; the Git hooks and CI verify the content regardless of who wrote it.

How memory works (why it stays coherent across many sessions)

The framework is built on five layers. Lower layers read from higher layers. The top two auto-load on every single session, so the agent always re-orients before doing anything.

Layer 1
Static contractThe spec. Changes only via a formal decision record (ADR).
Layer 2
Slow protocol - auto-loaded every sessionCLAUDE.md, project-config.md, the playbook, identity, gates. A SessionStart hook injects these so the agent can't "forget" to read them.
Layer 3
Per-milestone Phase docThe plan for the current milestone: stages, scope, the XML prompts pasted into each fresh session.
Layer 4
Per-session working memoryEphemeral. One stage's context. Cleared when the stage ends, on purpose.
Layer 5
Stage outputs - committed; some append-only foreverCode commits, retrospectives, the gap-analysis ledger, the build receipts. The audit trail. Append-only items are never rewritten.

How to use it

Get the kit (recommended: the release ZIP)

Download the starter ZIP from the releases page and verify it: the .sha256 checksum and, stronger, gh attestation verify (SLSA build attestation). The asset name follows the pattern sbak-<version>-starter.zip; the current release is sbak-v1.0.5-starter.zip.

Run the sequence from the folder the ZIP downloaded to (usually Downloads), and replace <projects-path> with wherever you keep code - the point is that the project gets a real home, not Downloads.

# macOS / Linux
unzip sbak-v1.0.5-starter.zip -d <projects-path>/my-project && cd <projects-path>/my-project
git init
node sbak/templates/scripts/kit-update.cjs --adopt
claude
# Windows (cmd or PowerShell)
mkdir <projects-path>\my-project
tar -xf sbak-v1.0.5-starter.zip -C <projects-path>\my-project
cd <projects-path>\my-project
git init
node sbak\templates\scripts\kit-update.cjs --adopt
claude

The adopt step verifies itself, and its exit code is the contract. Exit 0 means adoption COMPLETE: every required enforcement layer is active. Anything less exits non-zero and says why: exit 1 is ADOPTION INCOMPLETE with the missing control named and a repair: command that runs as printed. An incomplete install cannot silently look complete. Re-running --adopt is always safe; a clean re-run changes nothing.

Prefer to clone? The alternate path (same rule - give it a real home): git clone https://github.com/kknipe2k/Software-Build-Assurance-Kit.git <projects-path>/my-project, then cd <projects-path>/my-project, the same adopt step, and claude. One heads-up: origin still points at the kit's repository until the bootstrap resets it at handoff; don't git push before then.

Start

claude
# The kit's CLAUDE.md auto-loads.
# It echoes your folder first - confirm it's the right one.
# Then it asks the one question: Full or Custom.
# Then tell it what you want to build - a paragraph is enough.

Then

The agent runs bootstrap (spec, milestones, scaffold), replaces the kit's CLAUDE.md with your project's own, and hands off. From then on, every session inherits the calibrated methodology automatically. You approve at each stage boundary; the agent does the implementation.

The full session layer runs in Claude Code. Other agents work with the enforcement split above: the Git hooks and CI stay mechanical everywhere (the README's host table and the Copilot QUICKSTART cover that path). Cross-platform: the hooks are Node, which the kit already requires; no bash or WSL needed on Windows.

What you get · what it doesn't do

What you get

  • Calibrated ceremony: discipline scales to the project
  • A do-not-commit-without-approval guarantee, hook-enforced where the host runs hooks
  • Fresh-context verification that catches "tests pass but it's broken"
  • An append-only forensic audit trail (Full)
  • Validators enforced at pre-commit and in CI
  • Stack-agnostic: Rust, Python, TypeScript, Go, anything

What it doesn't do

  • Doesn't run the agent for you: you drive it
  • Doesn't mechanically enforce judgment: the hooks and CI enforce what they can check; the review gates stay human
  • Doesn't replace specs or design discussion: it frames them
  • Doesn't pretend Lite is auditable: pick Full if you need a trail
