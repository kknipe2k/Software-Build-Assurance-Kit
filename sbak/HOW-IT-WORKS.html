SOFTWARE BUILD ASSURANCE KIT

How It Works

A drop-in framework that turns Claude Code into a disciplined building partner. You describe what to build; it calibrates how much process to apply, then runs a structured loop with human approval gates, fresh-context verification, and an append-only audit trail.

What it does, in one picture

1 · DROP IN
Copy the kit into your project directory
Open it in Claude Code. The kit's CLAUDE.md auto-loads and takes over.
2 · CALIBRATE
Answer 5 questions
Project size, your experience, approval cadence, deliverable type, verification & CI cost. Sets how much ceremony and which gates apply.
3 · BOOTSTRAP
Spec → milestones → scaffold
Generates ~36 files for Lite, ~68 for Standard, ~69 for Full. Then hands off to the build loop.
4 · BUILD LOOP
Stages, verified, approved
Each milestone runs as stages. You approve before every commit.
5 · SHIP
PR per milestone
Code + retrospectives + audit ledger reviewed together, then merged.

The core promise: human reviews, agent implements, CI enforces. The agent never commits without your explicit approval — that rule holds in every tier and every mode.

Step 2 — Calibration (the 5 questions)

The first thing the framework asks. Each answer maps to settings stored in project-config.md. You can change them later via an append-only override log.

QuestionOptionsWhat it controls
Project size / complexity Lite Standard Full The tier — how much ceremony. Scaffold size, retrospective depth, whether the audit ledger is CI-enforced.
Your experience with the stack New · Familiar · Experienced The expertise — how much the agent narrates decisions, and whether it web-verifies best practices before coding.
Approval cadence Minimum · Standard · Maximum How often the agent stops for your review — per PR, per stage, or per micro-task.
Deliverable type CLI · Web-UI · Library · Service · Other The deliverable_type — orthogonal to tier. Decides which gates apply: web turns on a design brief (docs/design.md) plus browser-load and design-conformance verifier passes; library adds an API-surface contract; service adds endpoint contracts; cli adds command-surface checks. Usually inferred from your description rather than asked outright.
Verification & CI cost Local-first · Cloud · Local-only The verification_locus — where the test suite runs and what GitHub Actions costs. Public repo → cloud is free and unlimited; private repo → local-first (hybrid) keeps hosted minutes near-zero. Orthogonal to tier; usually proposed from repo visibility and whether the project ships to macOS.

Don't know? The safe default is Standard + Familiar + Standard (deliverable type inferred). Re-tiering later is cheap and tracked.

Stages A–D — Work

  • Test-driven: write a failing test, make it pass, refactor
  • All quality gates green; no skips, no --no-verify
  • Agent states its plan, you confirm, it works, it surfaces the diff
  • No commit until you approve. Then a fresh session opens for the next stage.

Stage V — Verifier

  • Fresh session with prior retrospectives deliberately hidden — the bias guard
  • Asks "does the code do what was promised?" not "did the tests pass?"
  • Four passes: inventory · wire-tracing · multi-call · runtime behavior
  • Findings graded blocks merge · carry forward · tech-debt

Stage E — Closeout

  • Cumulative review of everything shipped this milestone vs. the spec
  • Writes one entry in the append-only gap-analysis ledger (Standard & Full) — never edited, only appended; CI enforces this in Full tier
  • You review three artifacts together: the code diff, the retrospectives, and the ledger entry

Two roles — orchestrator and build (Standard & Full)

At Standard and Full tier, the agent runs as two distinct session types that never share a session. You — the human — are the conduit between them; only one acts at a time. These roles are the kit's agents — separated by hooks, not by request.

Orchestrator

  • Authors Phase docs, ADRs, protocol docs
  • Adjudicates the build's surfaces; routes Verifier findings
  • Sequences milestones; runs the PR and merge
  • Governed by ORCHESTRATOR.md — its own operating manual

Build

  • Executes one stage per fresh session from a pasted prompt
  • Does the TDD, runs gates, fills the retrospective
  • Does not sequence, route, or author Phase docs
  • Governed by CLAUDE.md + the stage prompt; never reads ORCHESTRATOR.md

Why split them: the build machine doesn't drift — each stage is a fresh scoped session. The orchestrator runs long, so it gets its own hardened manual to keep it from drifting. Recommended hosting: two Claude Code CLIs + git worktrees on one machine. At Lite tier the two roles collapse into one session.

How memory works (why it stays coherent across many sessions)

The framework is built on five layers. Lower layers read from higher layers. The top two auto-load on every single session, so the agent always re-orients before doing anything.

Layer 1
Static contractThe spec. Changes only via a formal decision record (ADR).
Layer 2
Slow protocol — auto-loaded every sessionCLAUDE.md, project-config.md, the playbook, identity, gates. A SessionStart hook injects these so the agent can't "forget" to read them.
Layer 3
Per-milestone Phase docThe plan for the current milestone — stages, scope, the XML prompts pasted into each fresh session.
Layer 4
Per-session working memoryEphemeral. One stage's context. Cleared when the stage ends — on purpose.
Layer 5
Stage outputs — committed; some append-only foreverCode commits, retrospectives, the gap-analysis ledger, the session register. The audit trail. Append-only items are never rewritten.

How to use it

Get the kit

git clone https://github.com/kknipe2k/Software-Build-Assurance-Kit.git my-project
cd my-project

Start

claude
# The kit's CLAUDE.md auto-loads.
# It presents the 5-question calibration interview as its first response.
# Answer the questions (or describe your project and let it propose a calibration).
# Then tell it what you want to build — a paragraph is enough.

Then

The agent runs bootstrap (spec → milestones → scaffold), replaces the kit's CLAUDE.md with your project's own, and hands off. From then on, every session inherits the calibrated methodology automatically. You approve at each stage boundary; the agent does the implementation.

Runs anywhere Claude Code runs — terminal CLI or the web app at claude.ai/code. Cross-platform (the hooks are Node, which Claude Code already requires — no bash/WSL needed on Windows).

What you get · what it doesn't do

What you get

  • Calibrated ceremony — discipline scales to the project
  • A do-not-commit-without-approval guarantee
  • Fresh-context verification that catches "tests pass but it's broken"
  • An append-only forensic audit trail (Standard+)
  • A schema validator enforced at pre-commit + CI
  • Stack-agnostic — Rust, Python, TypeScript, Go, anything

What it doesn't do

  • Doesn't run the agent for you — you drive Claude Code
  • Doesn't enforce gates itself — your CI does
  • Doesn't replace specs or design discussion — it frames them
  • Doesn't pretend Lite is auditable — pick Standard+ if you need a trail
